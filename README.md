## 🎯 1. ปัญหา ผู้ใช้ และคุณค่าที่คาดหวัง

### 1.1 ผู้ใช้หลักคือใคร (Target Users):
เจ้าหน้าที่จัดซื้อและวางแผนสต็อกของ BaanDee Living (Procurement / Stock Planning Staff) และหัวหน้าฝ่ายจัดซื้อ (Procurement Manager) ซึ่งทำหน้าที่พิจารณาและอนุมัติร่างคำขอสั่งซื้อ

### 1.2 ผู้ใช้กำลังพยายามทำงานอะไร (User's Job-to-be-Done):
ตรวจสอบและตัดสินใจทุกวันว่าควรสั่งซื้อสินค้ารายการใด จำนวนเท่าไร และเร่งด่วนเพียงใดก่อนสินค้าหมดคลัง โดยพิจารณาจากจำนวนสินค้าคงเหลือ ณ วัน Snapshot ยอดขายเฉลี่ยต่อวันย้อนหลัง 30 วัน และระยะเวลาจัดส่งของซัพพลายเออร์ (Lead Time) ร่วมกัน

### 1.3 ปัญหาในกระบวนการปัจจุบันคืออะไร (Current Pain Points):
ข้อมูลสินค้า สต็อก ยอดขาย และระยะเวลาจัดส่งกระจายอยู่คนละแหล่ง ทำให้เสียเวลาในการรวบรวมข้อมูลและตรวจสอบด้วยตนเอง อีกทั้งยังไม่มีเกณฑ์กลางในการประเมินความเสี่ยงสินค้าขาดสต็อก ทำให้แต่ละคนอาจตัดสินใจแตกต่างกัน การพิจารณาจากจำนวนสต็อกเพียงอย่างเดียวไม่สามารถบอกความเร่งด่วนได้อย่างชัดเจน และเมื่อข้อมูลไม่ครบถ้วนหรือผิดปกติ ก็อาจถูกละเลยหรือใช้การคาดเดาแทนการตรวจสอบ

### 1.4 ต้นแบบจะช่วยให้กระบวนการดีขึ้นอย่างไร (Value Proposition):
รวมข้อมูลจากหลายแหล่งโดยใช้ product_id เป็นคีย์เชื่อมโยงและแสดงผลบน Dashboard เดียว พร้อมประเมินความเสี่ยงสินค้าขาดสต็อกด้วยกฎที่กำหนดไว้แน่นอน (Deterministic Rule) และคำนวณระยะเวลาที่ควรสั่งซื้อจาก Days of Cover − Lead Time โดยค่าติดลบหมายถึงเลยกำหนดเวลาที่ควรสั่งแล้ว นอกจากนี้ ระบบจะแยกข้อเท็จจริงจากฐานข้อมูล เช่น จำนวนสต็อก Lead Time และ MOQ ออกจากค่าประมาณ เช่น ยอดขายเฉลี่ยและจำนวนสินค้าที่แนะนำให้สั่งซื้อ หากข้อมูลไม่ครบถ้วนหรือผิดปกติ ระบบจะแสดงสถานะ HUMAN_REVIEW_NEEDED พร้อมเหตุผล และระงับการสร้างร่างคำขอสั่งซื้อจนกว่าจะได้รับการตรวจสอบ เพื่อป้องกันการตัดสินใจจากข้อมูลที่ไม่พร้อม

### 1.5 ผลลัพธ์ใดเป็นเพียงสมมติฐานที่ยังต้องทดลองกับผู้ใช้จริง (Assumptions to Validate):
H1: Dashboard ที่รวบรวมข้อมูลไว้ในหน้าจอเดียวช่วยลดเวลาที่เจ้าหน้าที่ใช้ตรวจสอบรายการสินค้าที่มีความเสี่ยงได้จริงหรือไม่

H2: เกณฑ์ที่ระบบใช้จัดระดับความเสี่ยงสินค้าขาดสต็อกสอดคล้องกับการตัดสินใจของผู้เชี่ยวชาญด้านการจัดซื้อและการวางแผนสต็อกหรือไม่

H3: การแสดงสถานะ HUMAN_REVIEW_NEEDED พร้อมเหตุผล และการระงับการสร้างร่างคำขอสั่งซื้อเมื่อข้อมูลไม่พร้อม ช่วยลดความผิดพลาดจากการประเมินหรือการคาดเดาข้อมูลได้จริงหรือไม่

## 🧮 3. กฎความเสี่ยง สถาปัตยกรรม และ API

### 3.1 กฎประเมินความเสี่ยง (ไม่ใช้ AI)

`Days of Cover = สต็อกคงเหลือ ÷ ยอดขายเฉลี่ยต่อวัน (ย้อนหลัง 30 วันจาก Snapshot)`

| ระดับ | เงื่อนไข | ความหมาย |
|---|---|---|
| `CRITICAL_RISK` เสี่ยงสูง | Days of Cover **<** Lead Time (หรือสต็อก = 0) | ของจะหมดก่อนของใหม่มาถึง |
| `WARNING_RISK` เสี่ยงปานกลาง | Lead Time ≤ Days of Cover ≤ Lead Time + 7 | เหลือเวลาสั่งไม่นาน |
| `NORMAL` ยังไม่เสี่ยง | Days of Cover > Lead Time + 7 (หรือไม่มียอดขาย) | สต็อกเพียงพอ |
| `HUMAN_REVIEW_NEEDED` ต้องให้คนตรวจ | Lead Time ขาด/≤ 0, สต็อกขาด/ติดลบ, SKU ผิดรูปแบบ | ข้อมูลไม่พอ ระบบไม่เดา |

- **ควรสั่งภายใน (วัน)** = Days of Cover − Lead Time โดยค่าติดลบหมายถึงเลยช่วงเวลาที่ควรสั่งแล้ว ทั้งนี้ต้องแสดงผลตามค่าที่คำนวณได้และไม่ตีความว่าเป็นจำนวนวันคงเหลือก่อนสินค้าหมด
- **จำนวนแนะนำ (ค่าประมาณ)** = ยอดขายเฉลี่ยต่อวัน × (Lead Time + 14 วันสำรอง) − สต็อกคงเหลือ จากนั้นกำหนดค่าต่ำสุดเป็น 0 และหากต้องสั่ง ให้ปัดขึ้นเป็นจำนวนเต็มเท่าของ MOQ
- **กรณียอดขายเฉลี่ยต่อวันเป็นศูนย์:** ต้องจัดการแยกจากกรณีข้อมูลยอดขายขาดหาย โดยห้ามหารด้วยศูนย์ในการคำนวณ Days of Cover และควรแสดงเหตุผล/แนวทางตามนโยบายที่กำหนดไว้ หากข้อมูลยอดขายไม่ครบหรือไม่สามารถยืนยันได้ ให้ส่งตรวจสอบโดยมนุษย์แทนการเดาค่า
- **หมายเหตุการตรวจสอบ:** รายละเอียดข้างต้นเป็นกติกาที่เอกสารกำหนดไว้ ควรตรวจเทียบกับ `src/risk.py` และชุดทดสอบก่อนส่งงาน เพื่อยืนยันว่าโค้ดทำงานตรงตามเอกสาร

### 3.2 Tech Stack
- **Backend/Analytics:** Python 3.11+, `pandas`, `numpy`
- **API:** `FastAPI` + `Uvicorn`
- **Frontend:** หน้าเว็บ HTML/CSS/JavaScript (`web/index.html`) ให้บริการโดย FastAPI ไม่ต้องใช้ Colab หรือ Gradio
- **Storage:** CSV (`data/app_state/reorder_requests.csv`)
- **Testing:** `pytest`

### 3.3 API Endpoints
| Method | Path | หน้าที่ |
|---|---|---|
| GET | `/api/summary` | จำนวนสินค้าแต่ละระดับ, วัน Snapshot, รายการหมวด |
| GET | `/api/risk` · `/api/risk/{product_id}` | รายการ/รายละเอียดความเสี่ยง (กรองด้วย `status`, `category`, `q`) |
| GET | `/get_supplier_lead_time_api?product_id=` | **จุดเชื่อมต่อข้ามระบบ** ดึง Lead Time ซัพพลายเออร์ |
| GET / POST | `/api/requests` | ดู / สร้างร่างคำขอ (Create, Read) |
| PATCH | `/api/requests/{id}` | แก้จำนวน / อนุมัติ (Update) |
| DELETE | `/api/requests/{id}` | ซ่อนรายการ (Soft Delete) |

**API ข้ามระบบ: สถานการณ์ที่ต้องตรวจสอบ**
1. **200 OK:** พบข้อมูลและผ่านการตรวจสอบ → คืน `product_id`, `supplier_name`, `lead_time_days`
2. **404 Not Found:** ไม่พบ SKU หรือทรัพยากรที่ร้องขอ
3. **503 Service Unavailable:** ไฟล์ข้อมูลซัพพลายเออร์ขาดหายหรืออ่านไม่ได้ ทำให้บริการไม่พร้อมใช้งาน

กรณีพบ SKU แต่ค่า Lead Time ขาดหายหรือผิดปกติ ควรคืนสถานะ `HUMAN_REVIEW_NEEDED` พร้อม `review_reason` และใช้ HTTP status ให้ตรงกับสัญญา API ที่กำหนดไว้ อย่ารวมกรณี “ไม่พบทรัพยากร” กับ “พบข้อมูลแต่ข้อมูลไม่ผ่านการตรวจสอบ” โดยไม่แยกความหมาย ทั้งนี้ให้ยึดพฤติกรรมจริงใน `api/main.py` เป็นหลัก

### 3.4 ร่างคำขอสั่งซื้อ (ฟังก์ชันรอง)
ฟิลด์ที่บันทึก: `request_id`, `product_id`, `product_name`, `requested_qty`, `risk_status` (ณ วันสร้าง), `status` (`Draft` → `Approved`), `created_at`, `updated_at`, `is_deleted`
- เป็น **ร่างภายใน** เพื่อให้หัวหน้าอนุมัติ **ไม่ส่งคำสั่งซื้อจริงไปยังซัพพลายเออร์** (Human-in-the-loop)
- สินค้าที่เป็น `HUMAN_REVIEW_NEEDED` สร้างร่างไม่ได้ (API ตอบ 409)
- Soft Delete ตั้ง `is_deleted = True` โดยไม่ลบแถวออกจากไฟล์ (Audit Trail)

## 🎬  6. กรณีสาธิตหลักและผลลัพธ์ที่คาดหวัง

**กรณีที่ 1: การทำงานสำเร็จตั้งแต่ตรวจสอบความเสี่ยงจนถึงอนุมัติร่างคำขอสั่งซื้อ (End-to-End Success Flow)**

**1. คัดกรองสินค้าที่มีความเสี่ยง (Risk Filtering):** เปิดหน้า ตรวจความเสี่ยง แล้วเลือกคลิกการ์ดระดับควมเสี่ยงที่ต้องการดู ได้แก่ การ์ดเสี่ยงสูง การ์ดเสี่ยงปานกลาง และยังไม่เสี่ยง โดยระบบจะแสดงรายการสินค้าที่มีความเสี่ยงตามระดับการ์ดที่เลือก เพื่อให้เจ้าหน้าที่เลือกตรวจสอบสินค้าแต่ละรายการ

**2. ตรวจสอบข้อมูลและประเมินความเร่งด่วน (Risk Assessment):** คลิกสินค้าที่ต้องการตรวจสอบ เพื่อดูข้อมูลสต็อกคงเหลือ ยอดขายเฉลี่ยต่อวัน ระยะเวลาจัดส่งของซัพพลายเออร์ (Lead Time) สต็อกพอขาย (Days of Cover) และ จำนวนที่แนะนำให้ขอสั่ง ซึ่งช่วยประกอบการตัดสินใจว่าสินค้ารายการนั้นควรสั่งซื้อเร่งด่วนเพียงใด

**3. สร้างร่างคำขอสั่งซื้อ (Create Draft Purchase Request):** เมื่อพิจารณาแล้วว่าควรเติมสินค้า ให้กด สร้างร่างคำขอ ระบบจะสร้างร่างคำขอสั่งซื้อจากรายการสินค้าที่มีความเสี่ยง เพื่อให้ผู้ใช้ตรวจสอบก่อนดำเนินการต่อ

**4. ตรวจสอบ แก้ไข และอนุมัติร่างคำขอ (Review & Approve):** เปิดแท็บ ร่างคำขอสั่งซื้อ ตรวจสอบรายการและแก้ไขจำนวนที่ต้องการสั่งซื้อ จากนั้นกด อนุมัติ เพื่อบันทึกสถานะของร่างคำขอในระบบ โดยยังไม่ถือเป็นการสั่งซื้อสินค้าจริง

**5. ตรวจสอบการบันทึกข้อมูล (Data Persistence):** ปิดและเปิดโปรแกรมใหม่ แล้วกลับไปที่แท็บ ร่างคำขอสั่งซื้อ เพื่อตรวจสอบว่ารายการที่สร้างและอนุมัติไว้ยังคงอยู่ครบถ้วน

**ผลลัพธ์ที่คาดหวัง:** ผู้ใช้สามารถตรวจสอบความเสี่ยง พิจารณาข้อมูลสินค้า สร้างและแก้ไขร่างคำขอสั่งซื้อ ตลอดจนตรวจสอบได้ว่าข้อมูลยังคงอยู่หลังเปิดโปรแกรมใหม่

**กรณีที่ 2: กรณีที่ระบบต้องหยุดและส่งต่อให้มนุษย์ตรวจสอบ (Failure & Human Review Flow)**

**1. คัดกรองรายการที่ต้องตรวจสอบ (Human Review Filtering):** เปิดหน้า ตรวจความเสี่ยง แล้วคลิกการ์ด ต้องให้คนตรวจ เพื่อดูรายการสินค้าที่ข้อมูลไม่พร้อมสำหรับการประเมินตามปกติ

**2. ตรวจสอบข้อมูลที่ผิดปกติ (Data Validation):** กดเลือกดูสินค้าที่มีปัญหาคุณภาพข้อมูล เช่น SKU-0015 ซึ่งมีค่า Lead Time เป็น NaN หรือไม่มีค่าตัวเลขที่สามารถนำไปใช้คำนวณได้ตามปกติ

**3. ระงับการสร้างร่างคำขอสั่งซื้อ (Blocked Draft Request):** ระบบแสดงเหตุผลที่ต้องตรวจสอบ และไม่อนุญาตให้สร้างร่างคำขอสั่งซื้อสำหรับสินค้ารายการดังกล่าว เพื่อป้องกันการตัดสินใจจากข้อมูลที่ไม่พร้อม

**ผลลัพธ์ที่คาดหวัง:** ผู้ใช้ทราบสาเหตุที่สินค้าไม่สามารถประเมินได้ตามปกติ และระบบจะไม่สร้างร่างคำขอสั่งซื้อจนกว่าข้อมูลจะได้รับการตรวจสอบ

**กรณีที่ 3: การลบรายการแบบซ่อนข้อมูล (Soft Delete)**

**1. เลือกรายการที่ต้องการลบ (Select Item):** เปิดแท็บ ร่างคำขอสั่งซื้อ แล้วเลือกรายการที่ต้องการนำออกจากหน้าจอ

**2. ลบรายการออกจากหน้าจอ (Soft Delete):** เมื่อกดลบร่างคำสั่งซื้อในระบบ ระบบจะซ่อนรายการดังกล่าวจากหน้าจอ แต่จะไม่ลบแถวข้อมูลออกจากไฟล์ CSV จริง

**3. ตรวจสอบสถานะการลบ (Deletion Status):** ตรวจสอบข้อมูลในไฟล์ CSV จะพบว่าแถวรายการยังคงอยู่ โดยมีค่า is_deleted = True เพื่อระบุว่ารายการถูกลบแบบซ่อนแล้ว

**ผลลัพธ์ที่คาดหวัง:** รายการที่ลบจะไม่แสดงในหน้าจอตามปกติ แต่ข้อมูลเดิมยังคงอยู่ในไฟล์ CSV พร้อมสถานะที่ระบุว่ารายการถูกลบแล้ว

4. **เป็นเครื่องมือช่วยตัดสินใจเท่านั้น:** ระบบสร้างร่างคำขอภายในและเสนอจำนวนแนะนำ ไม่ส่งคำสั่งซื้อจริงไปยังซัพพลายเออร์ การอนุมัติควรเป็นไปตามกระบวนการที่กำหนด
